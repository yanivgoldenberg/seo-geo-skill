# Semantic acceptance inside the existing content workflow

Use `composed-content/2` for every new substantive content or service brief and release. This extends the existing fan-out, fair benchmark and original-improvement method. It does not replace the ordered process, native publishing controls, owner facts or approved authorization. Historical profiles remain readable only at their earlier acceptance level. A new draft missing this profile is incomplete, not grandfathered.

"100/100" may mean only that every applicable control in the declared, independently reviewed scope has current evidence and no unresolved finding. It is never a vendor semantic score, proof of Google deployment, or a guarantee of ranking, AI citation, traffic, meetings or revenue. An offline validator can verify declarations and bytes; a reviewer must still verify actual meaning, completeness, authenticity and usefulness. Label candidate, hosted Preview and public acceptance separately.

## One connected decision-to-release flow

1. Start with an evidenced buyer/ICP problem, entry channel and business decision. Separate observed demand, owner-approved capability, historical result, illustration and hypothesis. Preserve UNKNOWN where observation is missing.
2. Read the complete current source and rendered page, including inherited descriptions, tables, prices, FAQ/schema, CTAs and relevant locale counterparts. Bind the canonical source, renderer/configuration and proposed copy. Inventory coverage is not full editorial acceptance.
3. Fan out useful buyer subquestions: constraints, alternatives, evidence needed, responsibility, expected first output and next action. Each question has typed evidence, a reader task, an existing locale/type destination, offer connection and useful next action. Do not create one page per phrasing. Reuse/improve an existing answer unless a distinct unmet decision and proof justify a new route.
4. Read a dated primary competitor section under comparable buyer criteria. Adopt useful ideas in original work; do not copy text, testimonials, prices or results. Missing public detail is UNKNOWN, not proof of a competitor defect. "Skyscraper" names this bounded comparison, not market dominance.
5. Deliver the promised original artifact literally. A downloadable template requires a real file and working link; two variants require two actual messages; a worked example needs its actual inputs, output and limits; a research plan must remain labelled pending. "10x" means a useful original improvement, not more words or tenfold measured lift.
6. Review the ten semantic controls below for every affected page. Preserve useful authored descriptions while adding honest type/status labels. Derived labels/questions must refresh when source identity, body or locale changes and must never delete authored lookalike text. Current reviewed fingerprints or actual source evidence may support retained historical labels; a matching URL/title alone cannot.
7. Run native tests, claim/source review, CI, hosted Preview and current public verification at their actual stages. Candidate evidence cannot fill a public slot. CMS/canonical receiver readback and uncertain-effect reconciliation remain mandatory where applicable. Preserve rollback identity and failed attempts. A critical UNKNOWN blocks the dependent action. An owner-reviewed exception records its exact scope and remaining limitation; it never erases a native mandatory gate or becomes an unqualified 100.
8. Observe outcomes later with explicit cohorts, dates, denominators and exclusions. Search impressions/clicks, answer mentions, snippets, supported citations, referrer sessions, credible human sessions, CTA clicks, bookings, attended meetings, qualified opportunities and collected revenue are separate measurements. A bot user-agent, missing consent signal, unjoined record or absent report is not proof of a real human or zero demand. Keep unobserved outcomes UNKNOWN/PENDING; do not invent query-to-person joins or causal lift.

## Ten mandatory controls

| ID | Required review and failure condition |
|---|---|
| buyer_decision | A native reader can answer the intended buying/task question; headings or query coverage alone do not pass. |
| claim_evidence_status | Every material claim has appropriate attributable support and limits; hypothetical examples/results/plans cannot become historical proof. |
| original_useful_artifact | The promised decision aid, file, example, tool or workflow exists and helps the stated task; a description of an absent artifact fails. |
| locale_type_routing | Actual runtime collections, cards, navigation, canonical, hreflang and sitemap membership agree on language/type. No mixed-language archive or invented translation pair. |
| identity_offer_faq_parity | Visible copy, emitted schema/FAQ, approved identity/proof, price, scope, ownership and CTA promises agree. Absence is reviewed explicitly; no invented node is required. |
| metadata_date_parity | Actual changed content has consistent visible/own-schema/modified/OG dates; retain original publication and historical cohort dates. Inventory absence is explicit, not filled by invented dates. |
| contextual_link_journeys | Check authored in-body links separately from generated navigation/rails; follow relevant incoming/outgoing journeys and actual assets with locale/type intact. |
| derived_content_freshness | Changed body, locale or identity invalidates stale derived claims and evidence; source objects/authored nodes remain intact, repeated projection is idempotent. |
| reader_task_review | Read full rendered prose and perform the actual reader task, including mobile/RTL/accessibility where affected. Automated structure/model agreement cannot substitute for native meaning or aesthetic acceptance. |
| measurement_boundaries | Keep evidence levels and commercial stages separate, with current baseline, review window, cohort, denominator and falsifiable next decision. |

Every control is explicit PASS with current bound evidence and no findings for acceptance. A missing feature can pass only through evidence that it is genuinely absent and unnecessary for this page; blanket NOT_APPLICABLE is refused. Changing dependencies invalidates the relevant proof. Self-review must be labelled; independent reviewer identity cannot be fabricated.

## Record and executable integrity

Use a supplemental `fanout-page-map/1` review record selecting `method_profile: composed-content/2`, with the buyer-question/proof/method declarations described above. This is a new portable semantic supplement to the existing audit skill, not a claim that this repository already contains the private process or its research registry. The public command validates the mandatory semantic receipt subset; full source, claim, intent and comparison review remains the reviewer's task and the existing native audit/release gates remain required. Each page adds `content_type: BLOG_POST|GUIDE|SERVICE|HUB|UTILITY` and ten `semantic_checks`. Each row has `id`, `status: PASS`, `reviewer`, concrete `method`, `findings: []`, `revision`, exact `inputs`, `locale`, canonical `source_sha256`, proposed `content_sha256`, and bounded `{path, sha256}` evidence. Each subquestion adds `semantic_journey` with `reader_task`, `destination_type`, existing `offer_route` and `next_action`; the existing destination/proof/locale checks still apply.

Add `semantic_acceptance` with `schema: semantic-content-acceptance/1`, `phase: candidate|publication`, actual `reviewer`, `findings: []` and all seven `release_checks`: `source_review`, `local_checks`, `ci`, `preview`, `canonical_readback`, `production`, `public_readback`. PASS needs reviewer, matching revision/inputs and bound evidence. Candidate requires source/local PASS and explicitly PENDING later stages with reasons; it does not claim hosted or live acceptance. Publication requires all seven actual receipts. Keep phase-specific native checks proportionate to the actual change; never fabricate CI/CMS transactions for a content system that does not use them. A source-only system needs a separately reviewed integration adapter before selecting publication acceptance, not a false PASS.

## Research interpretation

Primary official documentation supports only what it actually states. Patents describe proposed/claimed mechanisms, not proof that a search product deploys them. Papers support results within their own data/model/intervention limits. Semantic buyer-question planning, retrieval, citation support and business outcomes remain separate. No LSI-density rule, minimum word count, proprietary score or FAQ rich-result promise is mandatory here. Preserve real facts and quotations; generated references/statistics are never evidence.

## Measure the workflow itself

Track lead time and rework per verified release, reopened/escaped semantic defects, false PASS found by independent or public review, stale-proof rejection, recovery without duplicate effects, and time/cost per verified useful outcome. Each metric names population/window and source. Then measure qualified traffic, qualified meetings, pipeline and revenue separately; release counts cannot increase those values automatically.
